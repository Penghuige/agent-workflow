# best-practices

## 职责

把"遵守 best practice"这类宽泛要求落成可检查的开工清单。产出归目标项目：
调研结论沉淀在项目 `docs/best-practices/`，随项目演化，同类任务只认真调研一次。
验收检查归 acceptance-checks，技能部署归 cc-switch-cli。

## 流程

1. **判型**：为当前任务命名类型（开发功能、合并分支、测试、发版、调试、重构……）。
   有成熟社区实践可依才继续；问答、纯阅读、单点小改动直接跳过本技能。
2. **查沉淀**：按项目 CLAUDE.md/AGENTS.md 的指针行找 `docs/best-practices/<任务类型>.md`。
   有记录：向用户简述要点，无异议后按记录执行；执行中发现记录与现状冲突，
   停下提请修订。无记录：进入调研。
3. **三源调研**：每源至少一条已核实出处，取不到就标推测：
   - 官方/社区通行流程：联网查权威文档（如 GitHub Flow、Conventional Commits、
     官方 testing guide），引用具体章节；
   - 成熟项目做法：选同语言同生态的知名开源仓库，看它此类任务的实际做法
     （CONTRIBUTING.md、CI 配置、提交历史）；
   - 项目自身约定：git log、CI 配置、lint 规则、已有文档中此任务类型的历史先例。

   来源间有分歧时逐条列出各源主张、原因、差异（如社区默认保留 merge commit，
   本项目历史一直 squash）。
4. **拍板**：把要求清单连同分歧表交给用户逐条确认或裁决；分歧未决不开工。
5. **沉淀**：定稿写入 `docs/best-practices/<任务类型>.md`，并在项目 CLAUDE.md/AGENTS.md
   加指针行。
6. **开工**：按定稿清单执行任务，清单条目即执行时的自查项。

## 记录格式

每个任务类型一个文件，条目含四要素：要求（可检查的动作）、理由（分歧时的取舍
记录）、来源（链接、命令或提交号）、日期。修订旧条目时保留原理由并注明变更。

## 停止条件

- 三源出处无法核实：标推测继续列出，但不进入拍板定稿。
- 用户未拍板：停在分歧表，不开工。
- 记录与项目现状冲突：先修订记录再执行，不绕过。
