# 测试方法选型与阶段交接

需要补充测试策略、选择现有 skills 或衔接执行与展示时读取。查看、接入已有结果时，
直接完成当前任务；已有测试流程和批准继续复用。以下是按需指南，不要求每次走完所有阶段。

## 能力与角色

先查宿主实际可用的 description，再读适用技能。下表名称是检索线索，不是跨宿主依赖。
每个阶段至多选择一个主流程，可叠加性质测试、浏览器等执行专长和验收约束；保留当前
适用流程，不重复启动等价流程。缺少 skill 时用可用工具完成已授权工作，并说明能力限制。

| 角色 | 可复用能力 | 选择与交接重点 |
|---|---|---|
| 测试实现主流程 | `tdd` 或 `superpowers:test-driven-development` | 公共行为、独立判据、实际红绿证据 |
| 输入域专长 | `property-based-testing` | 性质、生成域、固定边界、预算、收缩反例 |
| 页面执行与观察 | `webapp-testing` | 真实操作、状态断言、截图与日志 |
| 验收约束 | `acceptance-checks` | 视觉基准、数据量级、边界状态与隔离 |
| 故障诊断主流程 | `diagnosing-bugs` 或 `systematic-debugging` | 原始症状、最小复现、根因及针对性回归 |
| 代码审查主流程 | `code-review`、`requesting-code-review` 或 `code-audit` | 按变更审查、独立反馈或存量范围选择 |
| 反馈与结束检查 | `receiving-code-review`、`verification-before-completion` | 核实反馈、修复复验、结论对应实际证据 |
| 提交检查设施 | `setup-pre-commit` | 有建设需求时配置既有脚本，说明实际包含的检查 |
| 证据展示 | `test-dashboard` | 归一化结果、两轨、方法、缺口与详情 |

技能提供指导或脚本、项目已配置方法、本轮实际运行，是三件事。确认项目依赖、命令和
环境后再执行；提到某个框架不代表它已安装，也不代表它支持的专项测试已在项目配置。
视觉回归、可访问性、安全、性能、并发调度、覆盖引导 fuzzing 和实际变异测试，需各自
的工具或人工方法、判据和证据。一次截图、随机输入或一般人工检查不足以证明专项验证完成。

选择流程时处理实际差异：

- 两套 TDD 对重构时机有不同约定，沿用所选流程及项目要求，不混接相反的循环规则。
  先明确可观察行为与适用接口，已有确认复用；测试清单不等于一次性先写完所有测试代码。
- 审查需明确提交、staged、unstaged、untracked 中哪些在范围内，并核对所用命令。
  只比较到 HEAD 的命令不能证明工作区已被审查；缺规范或需求时保留该证据缺口。
- 诊断按一个主流程取证和试验；审查、验收与诊断结论分别保留，不当作测试执行通过。
- 项目与用户规则优先。相关证据仍适用时复用；工作树、环境或判据改变后重验受影响项。
  全量测试按实际风险与项目要求选择，不因另发一条消息重复运行，也不自动修复无关失败。

## 功能与证据对账

用户要求全面规划、扩大覆盖或判断各功能是否可用时，完成本轮范围的功能对账。仅接入
已有结果的任务保留原范围，并说明尚未评估功能完整性；不因显示历史报告重做全库测试。

1. **独立盘点功能**：从相关需求/验收条款和实际入口交叉查找用户可观察行为，按项目
   形态检查页面/路由、公开 API、CLI、后台任务及跨模块流程。源码中的入口不等于已实现
   需求；需求中有而未见实现的功能仍须保留。记录功能标识、来源、范围及实现已核实/未知。
   同一行为的多入口可归为一个功能并列出入口映射，保留各入口的证据缺口；不同角色、
   状态或契约的分支保留。已有清单可复用
   并补查差异；不能只从测试文件、测试名、代码行覆盖率反推功能全集。材料或扫描范围有限
   时注明范围未确认、未检查入口和排除理由，不宣称已完整盘点。
2. **逐功能选择场景**：每项核对正常路径的可观察预期，再考虑适用的异常/拒绝、输入
   边界、权限/业务组合、状态/操作顺序、依赖故障和数据一致性。按下节及项目风险补充
   并发、环境、性能等专项场景，以及本次改动可能影响的关联功能回归。不适用项注明功能
   或项目事实；仅缺材料、工具或执行授权时保留未评估/未执行，不据此判定产品不适用。
   缺判据项标待确认；不为每项强套全部方法。一个正常路径通过
   不能代表其他相关场景通过。
3. **区分计划与证据**：为场景保留判据出处、关联用例及对应轮次，核对测试实际断言是否
   验证该行为。测试名相似、工具已配置、脚本退出为0或代码被执行过都不能单独证明覆盖。
   建议用例标未实现/未执行；已有用例无结果、缺执行能力、采集失败或未接入分别说明。
   历史结果核对 revision、工作区、环境与适用条件，无法确认仍适用时标待复核，保留原结果。
   缺结果不能改成失败、跳过或通过，来源不一致不能凭名称强行配对。
4. **交付逐项核对表**：优先更新项目已有计划，记录下表；需要分层时按功能分组展开场景。
   这是人工可读的项目报告，不新增 v1 枚举，也不自动成为可信 runner inventory。

| 功能标识与来源 | 场景/适用性及理由 | 预期与依据 | 用例/实现情况 | 轮次/版本/环境与结果 | 缺口与下一步 |
|---|---|---|---|---|---|
| F1 改名 · 需求/入口 | 保存后刷新 | 新值保持 · 条款 | 用例已实现 | 历史轮，版本未知 | 待复核 |
| F2 导出 · 需求/API | 本人/越权 | 依条款或待确认 | 未见用例 | 无结果 | 补判据及用例 |

结论同时说明功能盘点范围及各场景的证据状态：哪些在本轮已约定判据下通过、失败、
尚未设计/实现/执行、受阻、待确认或待复核。若功能只测了正常路径，明确其他适用场景
仍缺证据；清单不完整时标明未知范围。功能数、用例数、通过记录数分别统计，只有分母、
映射和统计口径都可核实时才给相应覆盖指标。即使本轮约定场景全部通过，也只支持对应
版本、环境和范围的结论，不能宣布所有功能无缺陷。

## 按项目事实选择边界

围绕本轮关键行为及风险选择维度，结合 [项目风险与补测](risk-scan.md)；维度不是覆盖全集。
先确定预期行为来自哪条需求、契约、不变量或人工验收准则，再决定如何生成和执行用例。
缺判据时记录待确认点；没有异常也不能据此判定行为正确。

| 维度与适用事实 | 可考虑的方法 | 应保留的设计依据 |
|---|---|---|
| 输入范围、格式或解析 | 等价类、边界值、性质测试 | 有效/无效域、边界及邻值、独立预期 |
| 多条件规则或权限组合 | 决策表；必要时选组合测试 | 条件、可行组合、角色与资源归属 |
| 多步操作或状态约束 | 状态迁移、模型或探索路径 | 前置状态、合法/非法转换、状态不变量 |
| 外部依赖或故障恢复 | 集成、契约、故障注入 | 超时、错误响应、重试及恢复判据 |
| 共享写入或重复请求 | 并发、幂等性测试 | 调度顺序、参与者、最终状态及测试隔离 |
| 大数据或资源压力 | 量级验收、性能、稳定性 | 数据规模、负载、阈值、预算及停止条件 |
| 设备、环境或数据版本差异 | 兼容、可访问性、迁移与恢复 | 环境矩阵、基准、数据版本与恢复目标 |
| 安全敏感路径或断言质量风险 | 专项安全、覆盖分析、变异测试 | 允许目标、专项判据、报告及未评估范围 |

例如改名流程可按实际规则选择：空输入、长度边界、Unicode、无权修改、重复保存、保存中
离开、接口失败后恢复。候选场景须核对项目语义；未执行项留在计划/建议中，不生成历史步骤。
性质测试扩大的是生成器表达的输入域，随机操作扩大的是本轮尝试路径，均受判据和预算限制。

功能对账需要细化边界时，在对应功能下展开边界标识、事实/风险、判据、关联用例、
相关轮次和实际结果；单独做局部边界设计也可复用此记录。未评估、建议、已纳入计划、
已执行分别取证；矩阵有一行不代表已测。
仅在边界集合明确且映射有证据时讨论相应覆盖率，不把通过率或生成次数当作边界覆盖率。

## 阶段交接与 dashboard

字段、枚举和附件约束以 [结果与证据契约](result-contract.md) 为准。现有 runner 产物先由
项目适配器转换；没有现成转换器时显式说明并在当前范围实现必要适配，不能声称自动兼容。

| 阶段产物 | 向下一阶段交什么 | 在 v1 中如何展示 |
|---|---|---|
| 选型与计划 | 本轮范围、风险、判据、清单及未评估项 | `methods`、`gaps`；可信清单映射计划轨 |
| 测试实现 | 用例身份、实际行为、性质/生成域与复现资料 | `case.id`、`expected`；详细设计用报告 |
| 实际执行 | 命令、版本/环境、结果、输出及执行限制 | 独立 `runs`、用例状态、`actual/error`、日志附件 |
| 实际探索 | charter、实际动作、发现及判据 | 探索轨、`steps`、`findings`、截图/trace附件 |
| 验收与审查 | 基准、材料范围、结论及证据强度 | 原生报告、相关说明；只转换真实执行结果 |
| 修复与回归 | 原发现出处、新回归用例及修复后复验 | 保留原轮次；新轮次记录复验并链接项目材料 |

用 `methods` 记录相关方法及项目现状，关联实际 `run_ids`；补测机会留在 `gaps`，不自动
成为失败或已执行用例。无工具、环境受阻、采集失败、来源未接入按各自事实交付；项目方法
已配置但本轮没结果时，保留配置依据及缺失的执行证据。只有历史结果时仍按契约保留配置未知。

可信用例清单才可对齐已知未运行项；从部分结果推不出项目测试总数。一次性脚本或人工检查
有实际判据和执行记录也可接入，说明其形式；生成计划文本不能充当 runner inventory。

功能核对表、详细需求/边界矩阵与性质测试的生成预算、种子、收缩反例等，可放项目报告，并作为相关用例
的 `report` 附件；没有合适用例时沿用项目报告入口，不创建虚假通过用例承载附件。
附件只提供可阅读材料，v1 不计算矩阵覆盖，也不验证矩阵和结果之间的关系。扩展 JSON 字段
不会自动在页面展示；需要结构化需求关联或指标展示时另行设计对应契约和界面。

有价值的探索发现先在项目现有清单中保留“来源 run/case、发现与判据 → 回归用例”的关系，
再按已授权范围实施。v1 可展示其说明或报告，尚无发现转用例及跨轨关联的自动机制。
缺少正确回归接口时保留最小复现与限制，不用无关的浅层测试宣称问题已锁定。

交付前检查三件事：所选方法有项目依据；展示状态能追溯至实际材料；缺口、未执行与受阻
仍可见。页面生成成功只证明接入/展示成功，不能替代产品测试、发布判断或充分性结论。
