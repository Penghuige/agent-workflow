# 按测试工作方式组织界面

## 先回答人的问题

| 入口 | 页面应帮助回答 | 证据不足时 |
|---|---|---|
| 计划测试 | 哪些是本轮约定用例，哪些已运行、失败、跳过或尚未运行 | 无可信清单时不显示完整计划数量/完成率 |
| 探索测试 | 实际尝试了什么操作，在哪里遇到问题，怎样复现 | 无记录时显示尚未探索；无trace时不提供虚构回放 |
| 流程/来源 | 是否因环境、采集或未接入而缺结果，这份结果属于哪一轮 | 显式标出阻塞、采集失败、未接入及版本/环境限制 |
| 下一步 | 看哪份证据、运行哪条已批准命令、向哪个已有流程提交 | 缺负责人/入口时留待确认，不虚构角色或自动外发 |

## 界面深度

选择依据来自本项目可观察事实，不只依据代码行数或用户规模：
用例与步骤量、测试来源数、执行时长、环境/重试、共享资源与人员协作。

- **轻量**：两轨切换、范围说明、紧凑用例网格/列表和详情即可。数量少不代表环境简单，
  如有长任务或依赖阻塞，仍要显式展示。
- **多来源**：按测试层/模块分组，增加搜索、状态、来源/轮次筛选；缺失来源独立展示。
  不把同名测试跨环境、重试或批次去重。
- **复杂**：先给流程、轮次、环境和证据质量概览，再展开分组与用例详情；用分页或
  虚拟化控制 DOM。总览数量和当前页数量明确区分，操作后筛选与详情仍需对应。

这些层级由同一中央模板承载。项目通过配置 `layout` 选择 `auto`、`compact`、`grouped`
或 `workflow`；已有 v1 直接渲染命令仍可用 `--layout`。自动阈值只是初始选择，
按真实数据量验收后调整。分组来自来源标签与用例的 `suite` 等规范化字段，
项目特殊分类在采集器中映射，不为每个项目维护一份 HTML/CSS/JS。

接入配置与刷新流程见 [项目接入](project-setup.md)。中央模板承担通用界面变更，
项目采集器承担来源差异；先保持这条职责边界，再判断是否确有模板能力缺口。
已有原生报告满足需求时可直接保留其入口；统一面板补充跨来源概览时，也保留原生
trace 查看器、iframe 或其他已验证的查看能力，不能因统一样式而丢失证据下钻。

“管控”至少形成范围→执行证据→问题→下一步的闭环。页面内启动或重试仅在确有需求且
已有可接入口时实现；为该入口验证任务身份、状态、归属和并发约束。新增执行服务作为
单独范围讨论，不能只放一个按钮就宣称支持流程管理。

## 验收材料

- 小量：通过、失败、跳过、已知未运行、未知总数、无步骤/无附件空态。
- 中量：多来源/环境、筛选与分组数量、重试身份、部分接入、候选发现与确认问题。
- 大量：按声明目标数据量实测导航、搜索、筛选、分页及详情响应；不要渲染全部记录
  才让用户操作。用符合真实量级的合成材料，说明实际数据规模与测量环境。
- 共同：长名称/日志、手机宽度、键盘开关详情、非颜色状态标记、截图与行为检查，
  以及名称/错误中含 HTML 字符时的安全展示。断链或缺失证据不能伪装为可用。

同一 revision 不保证所有结果仍适用；同时展示执行时间、环境和范围。展示趋势需保留
真实历史，单轮数据不能推断波动率和问题发生概率。
