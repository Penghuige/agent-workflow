# auditing-skills（skill 审查员）

两个模式 + 全库体检，按场景选用。建前查重归 find-skills（本地→网络→新建）。

## 模式 1：执行验证（建后/改后）

按改动选层级，全部通过才算 GREEN：

- **Tier 0 静态结构**（任何改动都跑）：frontmatter 合规（name 小写连字符、description 只写触发条件含不触发场景、不写流程摘要——以 writing-skills 的 description 纪律为准）、无时效信息、篇幅（≤500 行）、安装入口一致性（检查实际存在的 ~/.cc-switch、~/.agents、~/.claude、~/.codex 技能目录；记录链接、实体副本和内容差异，不把各宿主布局一致当作必要条件，也不为修复暴露问题盲目新增重复入口）、文档风格（指令只留步骤/条件/动作/契约；理由按判据——删掉它遇到没覆盖的情况会做错吗，会就留、不会就删；比喻/口号/重复解释永远删）
- **Tier 1 可读性**（任何改动都跑）：零上下文 subagent 仅凭 SKILL.md 回答 3-5 个机制问题（含一个反向用例）
- **Tier 2 触发性**（动过 description 必跑）：给 fresh subagent 若干 skill 的 description 列表（混入 2-3 个干扰项）+ 两个场景（一个该触发、一个不该），要求选择并给依据
- **Tier 3 行为符合性**（动过流程必跑），按 skill 类型分流：
  - 非编排型：fresh subagent 拿全文 + 真实任务完整执行，对照流程逐步核对轨迹（步骤齐不齐、红线查没查、输出契约满不满足）
  - 编排型（自身要派 subagent 的）：主会话用低 stakes 问题实跑一轮；若有持久产物（笔记/报告），加查最近产物的契约符合度

## 模式 2：用后复盘

1. 收集失败现象（用户描述或会话记录）
2. 分类：触发失败（description）/ 理解失败（文本歧义）/ 执行失败（流程缺环节）/ 设计失败（机制本身错）
3. 给最小修复建议（形式匹配失败类型），修完回模式 1 重跑对应层级
4. 用户已授权修复时，备份后做最小改动并重跑对应验证；只有诊断授权时只给建议。沿用本会话已有授权，不重复索要确认。修复不重复建前查重；观察到的真实失败现象即失败基线（RED），无需另跑基线。

## 全库体检（用户喊"体检 skill 库"时）

1. 列出 ~/.cc-switch/skills/ 全部 skill 和宿主实际暴露入口；结合安装记录（`~/.agents/.skill-lock.json`）区分自建、上游套件、来源未知。插件技能（`~/.kimi-code/plugins/managed/` 下）一并列入范围。无上游记录不等于原创。
2. 检查：命名冲突、description 触发条件重叠、符号链接完整性
3. 长期未触发的 skill 提示用户（触发史来源：会话 recap 的 skill 使用记录；无证据就标"未知"，不猜）
4. 只出报告与处置建议，不动手；用户定夺。后续明确授权优化时进入模式 1/2，只改授权范围。上游套件默认保留；来源不明且不在用户指定范围内的技能不改。

## 触发与协作验证

- 选择测试混入相邻技能：深度决策 vs 想法评价/文献调研；项目设计学习 vs 代码定位/普通调试；修改中复查 vs 润色/投稿终审。正例、反例与组合任务都检查，记录实际选择及理由。
- 检查交接是否携带任务范围、已有产物路径、已确认约束、证据与假设、未决问题；下游应复用材料，不因转交而重新跑完整流程。
- 未做真实执行就只报告静态或选择测试结果；不能从描述清晰推断自动触发稳定。测试用独立临时目录，不改用户真实项目。
- 验证有 subagent 依赖时按宿主并发容量分批执行；不可用则标记未验证及原因，不以同上下文自审冒充独立验证。

## 红线（自检，踩了就重来）

- 只跑 Tier 1 就宣布"验证通过"
- Tier 3 用"读一遍觉得没问题"代替实际执行
- 复盘时替用户拍板修复方案
- 体检报告直接动手删/改 skill
- 越界做建前查重 —— 那是 find-skills 的职责
